# CLENCH — план реализации для Claude Code

Источник истины по продукту и экономике — `CLENCH-spec.md` в этом же репозитории. Этот документ не дублирует спеку, а превращает её в последовательность фаз, каждая с целью, задачами и критерием готовности (Definition of Done), пригодным для автономного выполнения агентом и для goal-режима.

**Порядок фаз обязателен.** Индексер идёт раньше программы, потому что от него зависят два параметра, которые нельзя выбрать умозрительно (шаг множителя, порог автовыплаты), и переписывать Anchor-программу после того, как она задеплоена, нельзя, а переписывать индексер — можно в любой момент. Фронт идёт последним, потому что его можно менять хоть каждый день, а деньги в контракте — нет.

Каждая фаза — самостоятельный `git` коммит/PR. Не начинать фазу N+1, пока не пройден Definition of Done фазы N, за исключением явно помеченных как параллельные.

## Фаза 0 — Каркас репозитория

**Цель.** Рабочее окружение, в котором можно запускать все последующие фазы, ничего продуктового ещё нет.

**Задачи:**
1. Монорепо со структурой:
   ```
   /program        — Anchor-программа (Rust)
   /indexer        — TypeScript, Postgres, Helius
   /keeper         — TypeScript, воркер
   /api            — Fastify
   /web            — Next.js
   /docs           — CLENCH-spec.md, этот файл, ADR по мере появления
   ```
2. `docker-compose.yml`: Postgres 16 + TimescaleDB extension, поднимается одной командой.
3. `.env.example` во всех сервисах, ничего секретного не коммитить.
4. CI: lint + typecheck на пуш, без деплоя.
5. `README.md` в корне со ссылкой на спеку и на этот план.

**Definition of Done:** `docker-compose up` поднимает пустой Postgres с включённым TimescaleDB, `anchor --version` и `solana --version` подтверждены в окружении, CI зелёный на пустом коммите.

## Фаза 1 — Индексер и калибровка параметров

**Почему первой.** Спека фиксирует шаг множителя (0.10/день, потолок 3× за 20 дней; для OG 0.15/день, потолок 4×) и порог автовыплаты (`RENT × 5` либо `MIN_PAYOUT`) как параметры, требующие проверки на реальном распределении холдеров. Если окажется, что до 20 дней без продажи доживает 2% кошельков, кривую придётся перекраивать — и это должно случиться до, а не после написания Anchor-программы.

**Цель.** Работающий пайплайн, который на исторических данных живого pump.fun-токена (Solana mainnet, произвольный токен возрастом от 30 дней) считает: (а) `min_balance_epoch` для каждого держателя за каждые сутки его жизни, (б) сколько кошельков дожило бы до 7/14/20 дней без падения баланса ниже 99.5% от начального, (в) распределение размеров позиций для калибровки порога автовыплаты.

### 1.1 Схема БД

Реализовать таблицы `balance_events` (hypertable) и `epoch_holders` ровно как в §7 спеки. Добавить служебную таблицу `calibration_runs` для хранения результатов прогонов (дата, токен, параметры, выводы).

### 1.2 Ingest

- Подключение к Helius (Yellowstone gRPC либо webhooks на старте — webhooks проще для разового исторического прогона).
- Для исторического прогона: обратный проход по слотам через `getSignaturesForAddress` + `getTransaction` для выбранного минта, извлечение балансовых дельт, запись в `balance_events`.
- Не проектировать под реалтайм в этой фазе — это разовый батч-скрипт для калибровки. Реалтайм-версия того же кода понадобится в фазе 3 (кипер), но интерфейс агрегатора должен быть общим для обоих случаев с самого начала, чтобы не переписывать дважды.

### 1.3 Агрегатор

Реализовать запрос на «ловушку открывающего баланса» из §7 спеки дословно: держатель без событий внутри окна получает баланс последнего события до начала окна.

Прогнать на выбранном токене за всю его историю, посуточно.

### 1.4 Калибровочный отчёт

Скрипт `calibration-report.ts`, который выводит:
- распределение длительности удержания (сколько кошельков продержалось N дней подряд, N = 1..30) — гистlimation;
- долю кошельков, которые дожили бы до текущего порога 20 дней при текущем допуске 0.5% (`dust_tolerance_bps`);
- распределение размеров позиций на конец каждой эпохи — процентили 10/25/50/75/90/99;
- при каком `MIN_PAYOUT` (в единицах SOL-эквивалента) доля кошельков, получающих выплату реже раза в неделю, не превышает 20%.

**Definition of Done:** отчёт сгенерирован на реальных данных минимум одного токена, результаты закоммичены в `/docs/calibration-report-v1.md`. Если фактическое распределение расходится с предположениями спеки более чем на порядок (например, до 20 дней доживает <5% кошельков, а не ожидаемые условно 15–20%) — **зафиксировать это как открытый вопрос к продукту и не продолжать в фазу 2 без явного решения**, потому что от этого зависят числа в конфиге программы.

## Фаза 2 — Anchor-программа: базовый цикл

**Цель.** End-to-end рабочий цикл на localnet без турниров и без OG: создание монеты, сбор налога, закрытие эпохи, публикация рута, автоматическая рассылка. Соответствует §2, §4, §5 (без турнирных аккаунтов) и §6 спеки.

### 2.1 Аккаунты и конфиг

Реализовать `Config`, `Launch`, `Distribution`, `Pending` по структурам из §5. Оставить поля турнира и OG в `Config`/`Launch` как заготовку (не реализовывать логику), чтобы не переделывать схему аккаунтов в фазе 3.

Три режима запуска (§2): `Standard`, `Reward`, `Competitive` как enum на `Launch`. В этой фазе реализовать полностью только `Standard` и `Reward`; `Competitive` создаётся, но без турнирной логики (флаг просто хранится).

### 2.2 Token-2022 transfer fee

`create_launch`: минт с расширением transfer fee, ставка 100–300 bps (валидация диапазона на инструкции), authority на fee отзывается в той же транзакции создания — необратимость должна быть проверена тестом, который пытается изменить fee после создания и ожидает ошибку.

### 2.3 Сбор и распределение налога

`harvest_tax`: атомарный сбор + сплит по `fee_split` + запись в `tax_this_epoch` — одной инструкцией, без исключений. Тест обязан проверять, что при падении транзакции между сбором и записью счёта состояние не рассинхронизируется (использовать Anchor's atomicity — CPI-фейл откатывает всю инструкцию).

`close_epoch`: только после `epoch_duration`. Фиксация `pot_snapshot`, обнуление счётчика.

`publish_root`: с проверками `total <= pool` и `vault.amount >= sum_undistributed + total` — оба теста на превышение должны явно проваливаться (negative test).

`distribute`: строгий порядок по `leaf_index`, обновление `Distribution.cursor`. Тест на попытку выплаты не по порядку — должен реджектиться.

Логика порога `Pending` (§4): реализовать `payout_threshold(owner, asset)` как чистую функцию, покрыть юнит-тестами на граничные значения (ровно на пороге, на 1 lamport ниже, выше).

**Definition of Done:** интеграционный тест на localnet проходит полный цикл `create_launch → harvest_tax (×N) → close_epoch → publish_root → distribute → finalize_distribution` для одного `Standard` и одного `Reward` запуска. Отдельный тест — рассылка на 10 000 синтетических держателей (сгенерированных, не реальных) укладывается в ожидаемое число транзакций и общий бюджет газа, посчитанный в §4 (~0.003 SOL на эпоху при выплате в SOL).

## Фаза 3 — Anchor-программа: турнир и OG

**Цель.** Полная механика §3 спеки поверх базового цикла из фазы 2, без изменения уже написанного кода фазы 2 сверх добавления новых инструкций.

### 3.1 Аккаунты

`Race`, `RoundResult`, `RoundsWon`, `TickerLock` по §5. Живой лидер без массива претендентов (`leader`/`leader_score` в `Race`, обновляемые через `update_leader`) — не хранить список участников нигде.

### 3.2 Матчинг по строкам

Реализовать `ticker_hash`/`name_hash`/`pair_hash` ровно по формулам §5. Отдельный юнит-тест: два минта с разным написанием одного тикера (`$PEPE`, `pepe`, `PEPE `) дают одинаковый `ticker_hash`; кириллический гомоглиф не совпадает.

### 3.3 Жизненный цикл турнира

`open_race`: автоматическое создание при обнаружении двух `Competitive`-запусков с совпавшим хешем и обоими выше `VOLUME_FLOOR`. Тест: не создаётся, если один из двух — `Standard` или `Reward`.

`join_race`: до конца второго раунда, только ровесники (`born_at >= race.started_at − 6h`), не заблокированные `og_barred`.

`update_leader`: пересчёт составного счёта (§3, формула `0.50×clean_volume + 0.30×holders + 0.20×capped_mcap`). **Эта инструкция зависит от данных индексера** (`clean_volume` требует направленного оборота по кошелькам, что считается офчейн) — спроектировать интерфейс между кипером и программой так, чтобы кипер передавал уже посчитанный составной счёт с подписью/проверкой на разумность (не превышает физически возможного по объёму пула за раунд), а не сырые данные. Задокументировать это явно как доверенный вход — это единственное место в системе, где офчейн-расчёт напрямую влияет на исход, и это нужно явно прописать в комментариях кода и в аудиторском чек-листе фазы 6.

`close_round` → `settle_race`: инкремент `RoundsWon`, при ничьей — продление (максимум 8 доп. раундов, дальше — суммарный налог, дальше — кто первым пересёк `VOLUME_FLOOR`). Всем проигравшим — `og_barred = true` необратимо.

`claim_og`: выдача плашки по порогам (`OG_VOLUME_FLOOR`, `OG_HOLDERS_FLOOR`, `OG_MCAP_FLOOR`), проверяется ежесуточно кипером, пока связка свободна.

### 3.4 Множитель для OG

Переключение формулы множителя (§2 «Множитель холда для OG-монет») в момент `is_og = true`, без сброса текущего стрика. Юнит-тест: холдер с 15-дневным стриком на монете, получившей OG на 15-й день, должен на 16-й день получить множитель по формуле `min(4.0, 1.0 + 0.15×16)`, а не начать отсчёт заново.

**Definition of Done:** интеграционный тест на localnet проходит полный сценарий: два `Competitive`-запуска с одинаковым тикером → турнир на 4 раунда без ничьей → `settle_race` → `claim_og` для победителя → проверка `og_barred` у проигравшего → попытка проигравшего создать третий запуск с той же связкой и включённым турниром отклоняется, с выключенным — проходит. Отдельный тест на ничью с продлением до предельных 8 раундов и последующим разрешением по суммарному налогу.

## Фаза 4 — Кипер

**Цель.** Автономный воркер, приводящий состояние программы в движение без ручных вызовов.

**Задачи:**
- `harvest_tax` по всем живым `Launch` каждые 5 минут.
- `close_epoch` / `close_round` по таймеру, с рандомизированным джиттером закрытия раунда (±15 минут, §3).
- `update_leader` на основе расчёта индексера (переиспользовать агрегатор из фазы 1, добавить composite score по формуле §3).
- `claim_og` — ежесуточная проверка всех `Competitive`-запусков без плашки на пересечение порогов.
- `distribute` пачками сразу после challenge window (1 час после `publish_root`).
- `sweep_pending` — раз в сутки для `Pending`, переросших порог, но не задетых обычной рассылкой.
- Ретраи с экспонентой на все permissionless-инструкции, идемпотентность (не дублировать `harvest_tax`, если предыдущий вызов не подтверждён).
- Алертинг (лог/вебхук) на любой `Underfunded`/`OverPromise` реджект — это должно быть невозможно, но если случилось, это критический сигнал.

**Definition of Done:** кипер запущен против localnet-валидатора с несколькими синтетическими запусками (включая один турнир) и самостоятельно, без единого ручного вызова, проводит их через полный жизненный цикл до выплат за сутки непрерывной работы в тестовом режиме (ускоренные таймеры).

## Фаза 5 — Индексер: production-режим

**Цель.** Перевести пайплайн фазы 1 из разового батч-скрипта в постоянно работающий сервис.

**Задачи:**
- Переключение ingest на Yellowstone gRPC для реалтайм-потока (вместо исторического батча).
- API поверх `epoch_holders`/`fighter_stats` для фронта и кипера (Fastify, только чтение, всё кешируется).
- Materialized view `fighter_stats` из §8 спеки, `REFRESH` по расписанию после каждого `close_epoch`.
- Артефакты эпох (§6): генерация JSON с листьями, пин в Arweave, публикация хеша.

**Definition of Done:** индексер обслуживает live localnet/devnet окружение, `fighter_stats` обновляется автоматически, артефакт эпохи пинится и хеш проверяем independent-пересчётом с нуля из публичного RPC.

## Фаза 6 — Аудит и подготовка к мейннету

**Цель.** Снять риски, зафиксированные в §5 и §13 спеки, до того как в контракте появятся реальные деньги.

**Задачи:**
- Автоматический скан (Sec3 / OtterSec или эквивалент) на Anchor-программу.
- Ручной чек-лист по таблице «Дыр» из §5: для каждой строки — тест, воспроизводящий сценарий, и подтверждение, что митигация работает.
- Особое внимание — доверенному входу `update_leader` (§3.3): формализовать, что именно проверяет программа при приёме составного счёта от кипера, и что произойдёт при компрометации кипера (worst case должен быть ограничен искажением исхода одного турнира, не кражей средств).
- Squads multisig на `authority`, upgrade authority под таймлок 48ч.
- `min_pot`, `og_volume_floor`, `og_holders_floor`, `og_mcap_floor` — финальная калибровка на основе отчёта фазы 1 и данных, накопленных за devnet-тестирование. Явно задокументировать, что `og_*_floor` калибруется с запасом вверх, а не вниз (§3: ошибка здесь необратима).

**Definition of Done:** отчёт аудита закрыт (все критические и высокие замечания исправлены), multisig активен, конфиг записан в `/docs/mainnet-config.md` с обоснованием каждого параметра со ссылкой на данные фазы 1/5.

## Фаза 7 — Фронт: MVP

**Цель.** Минимальный набор экранов из §8 спеки, достаточный для живого запуска первой монеты. Не реализовывать весь §8 сразу — порядок внутри фазы важен.

Перед началом — прочитать `/mnt/skills/public/frontend-design/SKILL.md` и применить направление «табло» из §9 спеки (см. также согласованные в чате визуальные референсы: глубокий чёрный, hairline-границы вместо заливок, единая гарнитура в духе Inter с вариацией по весу, edge-контраст между сторонами турнира синий/оранжевый, золото только для множителя и OG).

### 7.1 (обязательно для MVP)
- `/` — лента, сортировка Heat/Market Cap/New, панель турнира как приоритетный визуальный блок.
- `/coin/[mint]` — страница монеты с личным блоком холдера (множитель, прогресс до потолка, лента выплат вместо клейма).
- `/create` — форма запуска: выбор режима (Standard/Reward/Competitive), актив выплаты, ставка налога — с явным UI-предупреждением при ставке выше 1% (§2).

### 7.2 (следом, не блокирует запуск первой монеты)
- Автоматическое появление турнирной панели на странице монеты при обнаружении `Race`.
- `/w/[address]` — карточка бойца, `og.png` через Vercel OG.
- `/hall` — зал славы и позора.

### 7.3 (может идти параллельно с 7.2)
- `/docs` — правила, дословно раздел про то, что считается продажей (§7 спеки), позиционирование поддержки (§8) и границы полномочий.

**Definition of Done:** деплоер проходит путь от `/create` до живой монеты на devnet, видит свой множитель и ленту выплат на `/coin/[mint]`, лента на `/` отражает актуальное состояние из API фазы 5.

## Фаза 8 — Публичный devnet-запуск и наблюдение

**Цель.** Один реальный тестовый цикл перед мейннетом.

- Задеплоить 2–3 показательные монеты на devnet, минимум одна пара с совпадающим тикером для проверки турнира на реальном (не синтетическом) трафике участников тестовой группы.
- Собрать метрики: время от `create_launch` до первой выплаты, точность `min_balance` относительно ручной сверки по 10 кошелькам, фактическое распределение результатов турнира против ожиданий формулы.
- По итогам — обновить `/docs/mainnet-config.md` при необходимости, зафиксировать список известных ограничений MVP.

**Definition of Done:** отчёт о devnet-цикле, готовность идти в Фазу 6 (аудит) с финальными параметрами либо явный список того, что требует доработки перед аудитом.

## Не входит в MVP (сознательно отложено)

Явно исключить из скоупа до отдельного решения — упоминается в спеке как будущее, не должно случайно попасть в реализацию:

- Порт на EVM (§12 спеки).
- Лига между OG-токенами.
- Любые reward_kind за пределами `Sol | SingleAsset | Basket` (NFT-лотерея и подобное не обсуждались как решённые — не реализовывать).
- Featured slot и байбэк токена $CLENCH (§11) — отдельный трек, не блокирует запуск площадки.

## Как агенту двигаться по этому плану

- Каждая фаза — отдельная сессия/goal. Не переносить незакрытые TODO в следующую фазу молча — если Definition of Done не достигнут, это стоп-сигнал, а не повод продолжать.
- При любом расхождении между этим планом и `CLENCH-spec.md` — спека главнее, этот файл обновляется, а не наоборот.
- Фаза 1 может дать данные, требующие правки числовых констант в §2/§3 спеки (шаг множителя, пороги). Если это произошло — сначала правится `CLENCH-spec.md` с пометкой причины, потом код.
- Тесты пишутся вместе с инструкциями, не после. Инструкция без теста на happy path и хотя бы один negative test не считается завершённой для целей Definition of Done.

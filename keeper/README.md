# CLENCH — кипер (Фаза 4)

Автономный воркер, приводящий состояние программы в движение без ручных
вызовов инструкций: `harvest_tax`, `close_epoch`/`close_round`, `open_race`
(спека §5 — «зовутся кипером автоматически», не в явном списке §4 плана, но
без этого турниры никогда не начнутся сами), `update_leader`, `settle_race`,
`claim_og`, `publish_root`/`distribute`/`finalize_distribution`, `sweep_pending`.

## Запуск

```bash
cp .env.example .env   # заполнить SOLANA_RPC_URL / KEEPER_KEYPAIR_PATH / DATABASE_URL
npm install
npm run dev
```

## Демо-прогон на localnet (Фаза 4, проверено вручную)

```bash
solana-test-validator --bpf-program <PROGRAM_ID> ../program/target/deploy/clench.so
npx tsx scripts/demo-setup.ts       # создаёт Reward-запуск + 2 Competitive с одним тикером
# индексер ещё не в реалтайме (Фаза 5) — разово прогоняем историю для demo-минтов:
cd ../indexer && npx tsx scripts/local-ingest.ts <MINT> <CREATED_UNIX_TS>
cd ../keeper && npx tsx src/index.ts   # дальше кипер сам, без ручных вызовов
```

**Подтверждено прогоном:** турнир (`open_race → close_round ×4 → settle_race →
is_og/og_barred`) прошёл автономно до конца без единого ручного вызова
инструкции — дважды, воспроизводимо. Reward-цикл (`harvest_tax → close_epoch
→ publish_root → distribute → finalize`) распределил 94.8% пула эпохи
(2 425 217 210 из 2 557 673 016) автономно, прежде чем упереться в баг,
описанный ниже.

## Что нашёл и исправил этот прогон (а не выдумал заранее)

1. **`close_epoch` терял налог, если `publish_root` не успевал до следующего
   закрытия эпохи.** `epoch_pot_snapshot` перезаписывался, а не накапливался —
   пропущенная эпоха тихо теряла свой пул из учёта (токены оставались в vault,
   но не были ничьим обязательством). Исправлено в
   `program/.../close_epoch.rs`: накопление вместо присваивания,
   `publish_root` по-прежнему корректно вычитает опубликованное.
2. **Индексер не исключает служебные адреса (§7 «Кто исключён») при
   агрегации.** `tax_vault` (принадлежит Launch PDA, off-curve) попал в
   `epoch_holders` как «держатель» и сломал распределение на реальном
   PDA-адресе (`TokenOwnerOffCurveError`, uncaught). Временный защитный
   фильтр — `PublicKey.isOnCurve()` в `merkleLeaves.ts`; полноценная
   фильтрация по `Launch.excluded[]` в самом индексере — бэклог Фазы 5.
3. **`claim_og` может обогнать `open_race`, если `og_volume_floor` не выше
   `volume_floor`.** Обе Competitive-монеты получили OG независимо, гонка не
   успела открыться. Это не баг программы (каждая инструкция по отдельности
   верна спеке) — баг конфигурации; `og_volume_floor` обязан быть выше
   `volume_floor` в проде (спека сама предупреждает: пороги — «ставить с
   запасом вверх»).
4. `js-sha3`-импорт (`keccak_256`) требует деструктуризации default-экспорта
   под ESM — грабли, наступленные ещё в Фазе 1/2, повторно всплыли в новых
   файлах кипера.

## Известные ограничения (задокументированы, не забыты)

- `updateLeader`/`claimOg`/`settleRace` посылают `floorsMet`/composite score
  как частично доверенный вход (см. `update_leader.rs`) — в этой фазе
  `holders`/`mcap` не считаются вовсе (нет ончейн-оракула цены/ликвидности),
  используется fallback на `lifetime_tax_collected`, когда БД пуста (нет
  реалтайм-индексера для локальной сети — Фаза 5).
- Дерево выплат между `publish_root` и `distribute` хранится в памяти
  процесса (`treeCache`), не переживает рестарт — персистентность в БД
  нужна до продакшена, отдельная задача Фазы 5.
- `sweep_pending`/`claim_og`/`open_race` перебирают ВСЕ Launch/Race через
  `.all()` — не масштабируется на тысячи одновременных запусков без
  индексации/пагинации; для MVP-нагрузки достаточно.
- Один Pending, оставшийся от распределения со сломанным листом (см. пункт 2
  выше) в этом конкретном демо-прогоне навсегда застрял на cursor 4/6 —
  корень уже опубликован на цепи с плохим листом, задним числом не
  исправить. В проде это не повторится (фильтр уже стоит до публикации).
